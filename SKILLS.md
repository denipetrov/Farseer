# Farseer: reference for agents

Farseer is the World of Warcraft front end served at **https://rankwarden.gg**. It shows
leaderboards, characters, guilds and widgets. All of its data comes from the
**Soulseeker** API (`https://api.rankwarden.gg`, or `http://localhost:3001` locally).

This file is for agents and maintainers who change, test or deploy Farseer. It records
decisions, conventions, traps and recipes that the code alone doesn't make obvious.
[README.md](README.md) is the human overview, and [docs/soulseeker.md](docs/soulseeker.md)
is the integration guide.

**Where to start:**

- To **add a page or call an endpoint**, read §4 (API layer), §5 (routing) and §6 (styling).
- To **look up an endpoint's parameters or response**, use §3. Never guess them.
- To **test** a change, read §8. Before you run anything on Windows, read §9.
- To **deploy**, read §10.

**Keep this file current.** When you add a convention, find a trap, or change a decision
recorded here, update the section in the same change. Add an entry to §12 when the change
is a decision.

## 1. Agent directives

- **Do not commit, push or merge** unless the user asks.
- **Never modify the sibling repositories** (`../Soulseeker`, `../Rankwarden`,
  `../blizz-auth`, `../spirit-link`). Reading them is fine. If Farseer needs a change there
  (a CORS origin, a new field, an endpoint), write it up as a proposal for the user.
- **Never print or persist a credential.** That covers `.env` values from any repo,
  tokens, and decoded Secrets. Read only the specific key you need, for example
  `grep ^KEY= .env | sed 's/=.*/=<set>/'`.
- **Never hard-code the API URL.** It comes from runtime config (§7).
- **Never call `fetch` for Soulseeker directly.** Go through `api` from `@/api` (§4).
  Otherwise the bearer token, renewal and the retry on 401 are all skipped.
- **Raw hex colours live only in `src/styles/palette.ts`** (§6).
- **Keep the dev server on port 5173.** It is the only local origin that Soulseeker's CORS allows.
- **The Kubernetes namespace is `farseer`.** The image is `ghcr.io/denipetrov/farseer`.

## 3. Soulseeker: where the truth is

- **The Soulseeker Handbook**, https://claude.ai/artifact/NinpdHpweHpZmjF6N5kmxv, documents
  every endpoint with its parameters and response.
  - Read it with the claude-artifacts `read_artifact` tool. The Docs `read` tool is refused for it.
  - The result is about 100k characters and is saved to a JSON file. Extract the text with Python, then read the text in chunks.
- **`../Soulseeker/SKILLS.md`** has more detail. Where it and the handbook differ, SKILLS.md wins.
- **Swagger** is at `http://localhost:3001/docs` when Soulseeker runs locally.
- **Ask the running service.** Soulseeker is usually running locally, with Redis and Rankwarden's MongoDB in Docker.
  Check it with `curl localhost:3001/health`, then probe real responses before you type
  them. A token request needs the header `-H 'Origin: http://localhost:5173'`.

Facts that shape the UI (the full list is in docs/soulseeker.md):

- **Regions.** PvP boards accept `us eu kr tw world`. The PvP character accepts `us eu kr tw`. PvE characters and guilds also accept `cn`. Mythic+ and raid boards default to `world`.
- **Required PvP leaderboard parameters:** `region`, `seasonId` and `bracket` (`2v2 3v3 rbg shuffle blitz`, or a spec ladder such as `shuffle-mage-fire`). `class` and `spec` are optional, and a spec always comes with its class.
- **Paging.** Send `page` (starts at 1) and `pageSize` (max 100). Answers include `total` and `totalPages`.
- **Shares differ by endpoint.** PvP `share` is 0–1. PvE `percent` is 0–100.
- **`"stale": true`** on character and guild pages must be shown to the user.
- **`isFullyCovered: false`** on the Mythic+ leaderboard means the score is partial. Flag it in the UI.
- **503 + `Retry-After: 60`** means Soulseeker's upstream budget is spent. Show "try again shortly"; don't retry.

## 4. API layer (`src/api/`)

```
src/api/
  index.ts              the app instances: `api`, `auth`; re-exports ApiError
  client.ts             createApiClient: bearer token, one renew + retry on 401
  auth/tokenManager.ts  createTokenManager: anonymous grant, refresh, cross-tab safety
  errors.ts             ApiError { status, code, message, retryAfterSeconds?, issues? }
  queryClient.ts        QueryClient defaults and the retry policy
  session.ts            GET /session: the example to copy for new endpoints
  pvp.ts                PvP seasons, leaderboard, bracket list
  pve.ts                PvE catalogue: GET /pve/raids, GET /pve/mplus-seasons
  gameNames.ts          GET /i18n/names
```

### Adding an endpoint

Put each endpoint area in its own file (`src/api/pvp.ts`, `src/api/pve.ts`, ...). Export
the response types and a `queryOptions` factory, following `session.ts`:

```ts
export const pvpLeaderboardQuery = (p: LeaderboardParams) =>
  queryOptions({
    queryKey: ['pvp', 'leaderboard', p],
    queryFn: ({ signal }) => api.get<LeaderboardPage>('/pvp/leaderboard', p, signal),
  });
```

- **Always pass `signal`**, so that a cancelled query aborts its request.
- Type responses from the real answer: probe the local service or read the handbook.
- `undefined` and `null` parameters are left out of the query string automatically.

### Auth: rules that must survive refactors

These are tested in `tokenManager.test.ts` and `client.test.ts`. Keep them passing.

1. **The anonymous grant** is `POST /oidc/token` with a form-encoded body:
   `grant_type=urn:soulseeker:grant-type:anonymous` and `client_id=soulseeker-web`. The
   browser sends `Origin` itself, and it must be in Soulseeker's `CORS_ORIGINS`.
2. **Access tokens live 600 s.** They are renewed 30 s before they expire (`expiryMarginMs`).
3. **Refresh tokens rotate on every use, and reusing one revokes the whole session.**
   - Within a tab, concurrent callers share one in-flight renewal.
   - Across tabs, renewals run under `navigator.locks` (`farseer:auth:renew`). Inside the
     lock the manager reads **storage, not memory**, and adopts a token another tab already stored.
   - A `storage` event updates other tabs' in-memory copies.
4. **On a 401**, `handleUnauthorized(rejectedToken)` returns the current token if it was
   already renewed; otherwise it renews. The client retries **once**. It never retries
   when `WWW-Authenticate` says `insufficient_scope`.
5. **When a refresh answers `400 invalid_grant`**, the manager clears the tokens and makes
   a new anonymous grant. Any other failure (network, 429, 5xx) is thrown and the refresh
   token is kept.
6. **Tokens are persisted** in localStorage under `farseer:auth`, so a reload doesn't
   spend a grant (the limit is 10 per IP per minute). If storage is blocked, tokens stay in memory.
7. **React Query retries** only network errors and 5xx other than 503. It never retries
   4xx, 429 or 503. 401s are handled by the client, not by React Query.

Soulseeker's real answers (probed on 2026-11-17):

| Case                        | Status and body                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------- |
| Grant OK                    | `200 { access_token, refresh_token, expires_in: 600, token_type, scope: "api:read" }` |
| Reused or bad refresh token | `400 { error: "invalid_grant" }`                                                      |
| No token                    | `401 { error: "invalid_request" }`                                                    |
| Bad or expired token        | `401 { error: "invalid_token" }`                                                      |
| Missing or unlisted Origin  | `403 { error: "access_denied", error_description: "origin not allowed" }`             |
| Nest errors                 | `{ statusCode, message, error: "Not Found" }`, mapped to code `http_<status>`         |

Through CORS, the browser can read the `retry-after` and `www-authenticate` headers.

## 5. Routing (`src/routes/`)

- File-based. A `$param` segment in a file name is a path parameter, and dots separate
  segments (`$game/$locale/pvp/character/$region.$realm.$name.tsx` →
  `/$game/$locale/pvp/character/$region/$realm/$name`).
- **Every page lives under its game, then its language** (`src/routes/$game/$locale/`, the
  user's choice of 2026-11-26): `/retail/en/pvp`, `/retail/de/pve/character/eu/draenor/x`.
  - **Games** (`src/lib/games.ts`): `retail` and `forever`, the two WoW games. Only Retail
    has data, so Forever is defined with `enabled: false`: its addresses redirect to the same
    page on Retail. To open it: set `enabled: true`, add the game switch to the header (a
    toggle like PvP/PvE), and pass the game to Soulseeker once its API takes one. The legal
    pages are per game too (`/retail/en/privacy`), with the same text: a game-independent
    `/en/privacy` would clash with `/<game>` as the first segment.
  - **Linking:** `useSite()` (`src/lib/site.ts`) gives `{ game, locale }` for the current
    page. Pass it as the params: `<Link to="/$game/$locale/pvp" params={site}>`, or
    `params: { ...site, bracket }`. The menu builders take it (`pvpNav(site, name)`,
    `pveNav({ site, … })`).
  - **Canonical addresses** (`canonicalPath` in `src/lib/sitePath.ts`, run by the root
    route): `/en/pvp/…` (old links) → `/retail/en/pvp/…`; `/pvp/…` →
    `/retail/<preferred language>/pvp/…`; `/forever/…` while off → `/retail/…`;
    `/retail/de_DE/…` → `/retail/de/…`; `/retail` → `/retail/<preferred language>`. Unit
    tested in `sitePath.test.ts`.
  - Code that builds paths by hand keeps the game: the PvP/PvE switch, the language switch
    (swaps the second segment) and links inside legal documents (`/privacy` →
    `/<game>/<lang>/privacy`). `gameModeOfPath` skips the game and language.
  - See "Languages" below.
- **URL search params are the data filters.** Every board keeps its filters in the URL,
  so a page can be shared and the back button works.
- `validateSearch` with a plain function: TanStack treats its output type as the input
  type for `<Link search>`. So **make every search field optional** and apply defaults
  when reading (see `validateLeaderboardSearch` in `src/lib/leaderboardSearch.ts`). Drop invalid values to `undefined` instead of throwing.
- The router context carries `queryClient`. A loader can prime data with
  `context.queryClient.ensureQueryData(someQuery(...))`.
- Route files are code-split by the plugin (`autoCodeSplitting`), and the
  `react-refresh/only-export-components` lint rule is off for `src/routes/**`.
- The root route has a `notFoundComponent` and an `errorComponent`.
- **Game modes.** The site has two halves, PvP and PvE (`src/lib/gameMode.ts`), each with
  its own home: `/<game>/<lang>/pvp` and `/<game>/<lang>/pve`. Put each mode's pages under
  its prefix.
  - `/` and `/<game>/<lang>` have no page: they redirect to the remembered mode (preference
    `gameMode`, default `pvp`), `/` in the default game (Retail) and the preferred language.
  - `useGameMode()` (`src/preferences/useGameMode.ts`) gives the current mode and a
    switch. Under `/<game>/<lang>/pvp/…` or `…/pve/…` the URL decides and is remembered, so
    a shared link sets the mode; elsewhere (character, guild, leaderboards) the remembered
    mode applies. Switching remembers the mode and opens its home in the current language.
    The logo links to the current mode's home.

**Languages** (`src/i18n/`). Eight, each with a short URL slug the user chose:

| Slug | Soulseeker `locale` | Shown as  |
| ---- | ------------------- | --------- |
| `en` | `en_US`             | English   |
| `es` | `es_ES`             | Español   |
| `pt` | `pt_BR`             | Português |
| `fr` | `fr_FR`             | Français  |
| `de` | `de_DE`             | Deutsch   |
| `ru` | `ru_RU`             | Русский   |
| `ko` | `ko_KR`             | 한국어    |
| `cn` | `zh_CN`             | 简体中文  |

- **URL.** The language is the first segment. `resolveLocaleSlug` reads any spelling
  (`DE`, `de_DE`, `de-de`, `kr` → `ko`, `zh` → `cn`); the `$locale` route redirects it to
  the slug. A path whose first segment names no language (`/pvp`, `/character/…`) gets the
  preferred language put in front by the **root** route's `beforeLoad` (a path like
  `/character/eu/x/y` matches nothing under `$locale`, so that route's checks never run).
- **Preferred language** (`preferredLocale()`): the remembered one (preference `locale`,
  set whenever a language URL is opened or the dropdown is used), else the browser's
  (`navigator.languages`, first match by language: `de-AT` → `de`), else English.
- **The front end's own text**: `src/i18n/messages/<slug>.json`, flat keys
  (`"search.noMatches"`). `en.json` is the source and its keys are the `MessageKey` type.
  Read it with `const { t } = useI18n(); t('guild.logo', { name })`; `{placeholders}` are
  filled from the params. English is bundled; the others load before the `$locale` route
  renders (no flash of English). **Every new static string goes in all eight files**:
  `messages.test.ts` fails on a missing or extra key, an empty value, or a placeholder that
  differs from English. Use WoW's own terms for the language (Horda, Allianz, 방어 전담).
- **Game names**: `GET /i18n/names?locale=<code>` (`src/api/gameNames.ts`), prefetched by
  the `$locale` route's loader on every load, cached an hour. `useI18n().name(kind, id,
englishFallback)` looks up classes, specs, races, hero talents, affixes and dungeons by
  the ids the API sends; until the answer arrives, and for anything Blizzard has no name
  for, our English name is used. Icon labels (class, spec, race, hero talent) use it.
- **PvE catalogue**: `GET /pve/raids` (every raid with bosses, icon, `starts`/`ends` per
  region) and `GET /pve/mplus-seasons` (every season with dungeons and cutoffs, plus all
  affixes), in `src/api/pve.ts`. The PvE menu and many PvE pages need them, so
  `usePveCatalogue(mode === 'pve')` in `RootLayout` fetches both as soon as the visitor is
  on the PvE side (a `/pve/...` URL, or PvE chosen on a shared page) and never on PvP.
  Readers use `useQuery(raidsQuery())` / `useQuery(mplusSeasonsQuery())`: the same cache
  entries, no second request. Raids are stale after 6 h, seasons after 30 min (live
  cutoffs). Both are newest first; `ends.<region>` null means still open, and
  `isRunningIn(entry, region)` says whether a raid or season runs there now. Names are
  English: translate raids, bosses and dungeons by slug and affixes by id with `/i18n/names`.
- **Codes the API sends** get translated labels from `src/i18n/labels.ts`: `regionLabel(t,
'eu')`, `roleText(t, kind)`. The English helpers in `src/lib/wow/` stay for code without
  a translator.
- `<html lang>` follows the URL's language (`htmlLang`, e.g. `de-DE`).
- **Not translated yet:** PvP rank and honor badge names (`PvpRankIcon`, `HonorBadge`), as
  nothing shows them yet. "PvP" / "PvE" stay as they are: the mode art carries them.

**The header** (`src/components/AppHeader.tsx`) is a three-column grid:

- left: the logo, the language dropdown (`header/LanguageSelect`: the current code,
  `DE`, opening a list of the eight in their own names; choosing one swaps only the URL's
  first segment and keeps the path, search and hash) and the PvP / PvE switch
  (`header/GameModeToggle`, the `game-modes/pvp|pve` art, which carries its own label);
- centre: `header/SearchBar`;
- right: the icon style switch (`header/AssetStyleToggle`, showing
  `icons/styles/<style>-<faction>.png` for the user's faction, unfiltered and underlined in
  the accent like the faction switch) and the faction switch (`FactionToggle`, the emblems in the chosen style).

The header is `position: sticky; top: 0`. A sticky element only sticks within its parent, so
`#root` (its parent) must grow with the page: `min-height: 100%`, **never `height`**
(`src/styles/global.css`). A fixed-height `#root` let the header scroll away after one screen.
Never give an ancestor of the header `overflow` other than `visible` either.

The outer columns are `minmax(max-content, 1fr)`, so the search stays centred and is never
covered. Below 1100px the search moves to a row of its own.

**Mobile (820px and below)** the header is the menu button and the search, on one row
(61px tall). Everything else (logo, language, PvP / PvE, icon style, faction) is in the
menu's drawer, `header/MobileMenu`, one below the other with a label each:

- A left overlay (`min(22rem, 88vw)`, portal to `body`), opened by the three-bar button
  (drawn in CSS; there is no `nav/menu.svg`). A modal dialog: focus starts on the close
  button and Tab wraps inside (counting only what Tab reaches: unchosen radios are
  `tabindex -1`); Escape (listened for on `document`, so it works wherever focus is), the
  backdrop or the close button closes it and focus returns to the menu button; the page
  behind doesn't scroll. Escape on the open language list closes only the list.
- Any navigation closes it (mode, language, the logo, a link); faction and style don't.
- **The left menu** (`SideNav`) goes in as `<MobileMenu>{…}</MobileMenu>` in `AppHeader`: it
  shows below the settings, after a trim divider.
- Measured 2026-11-25: above 820px the desktop header fits without overlaps in every
  language; at 820px and below its two sides don't, hence the drawer. After a header
  change, scan widths 360–1400 for overlapping controls (compare the bounding boxes of
  the visible `header a, header button, header input`).

All three switches are `header/IconToggle`: a
radio group (arrow keys move the choice). The art is **never filtered or backed**: not
chosen, it is only fainter (60%, still in colour); the chosen one has a bar underneath, in
the accent (mode, style) or the option's own `underline` colour (each faction its own). The
user rejected greyscale, glow, drop-shadow outlines and a plate behind the art as making the
emblems invisible, blurry or untrue to the files. Its icon size is the CSS var
`--toggle-icon-size` on the group, so a layout can override it.

**Showing a character** (`src/components/CharacterLine.tsx`): everywhere a character is
listed (search, boards, rosters), use `<CharacterLine>`, the user's fixed order:

    [race] [class] [spec] [hero talent]  Name <Guild>          [faction]
                                         Realm · Region

- The faction sits at the far right of the row (it didn't fit beside the round icons).
- Every slot is always filled: an icon the data doesn't give, or a value with no file,
  shows `info/unknown.png` (`<UnknownIcon label="Unknown spec" />`). Rows keep one shape,
  so names line up. An unenriched PvP character is four question marks.
- PvE characters have no hero talent slot at all (`showHeroTalent={false}`): the API never
  gives one and the user doesn't want it there.
- Pass ids first (`classId`, `specId`, `raceId`, `heroTalentId`), names as the fallback.
- The name is in the class colour; the guild in `<>` only when given.
- **Guilds** use `<GuildLine>` in the same shape: `[logo] Name / Realm · Region [faction]`.
  The logo is the URL the data gives (Raider.io's CDN: a custom logo or its generic faction
  icon); with none, or one that fails to load, it is `unknown.png`. The faction slot shows
  only when the source carries a guild faction (pass `faction`; `null` = unknown). Search
  suggestions send `logo` and `faction` (Soulseeker 839629d, 8de63f6). Soulseeker caches
  suggestions in Redis per prefix, so an answer cached before a field was added lacks it
  until the cache expires; `GuildLine` then just has no faction slot. Shared row styles: `src/components/lineParts.module.css`.
- `regionName()` (`src/lib/wow/regions.ts`): `us` Americas, `eu` Europe, `kr` Korea, `tw`
  Taiwan, `cn` China. `realmLabel()` shows a realm slug as words when the data has no name.

**The left menu** (`src/components/nav/`): the current game mode's site navigation.

- **Where:** a sidebar on desktop (`Sidebar` in `__root.tsx`, 17.5rem). The column runs the
  full height down to the footer and carries the border; the menu inside (`SidebarInner`)
  is sticky right below the header and scrolls on its own. Don't make the column itself
  sticky: its border then stops where the menu ends, which looked cut off. At 820px and
  below it is the bottom of the mobile drawer (`<MobileMenu>` children in `AppHeader`).
  Both modes have one; `SideNav` picks `pvpNav` or `pveNav`.
- **The model** (`navTypes.ts`): `NavLink`, `NavGroup` (children nest to any depth;
  `defaultOpen` opens it on arrival; an optional `link` gives the section its own page) and `NavNote` (a muted line: "Loading raids…"). A
  label is a message key or `{ text }` (a game name already translated). An icon is a
  single-colour SVG path (drawn by `NavGlyph`) or game art drawn as it is:
  `{ kind: 'class' | 'spec' | 'role' | 'image' }` (`image` is a URL from the data, null or
  broken → the unknown icon). Art sits in a slot of the glyphs' width so labels line up.
- **Sections with their own page** (`NavGroup.link`; the PvP brackets, the user's rule of
  2026-11-27): the label is a link to the page and **only the arrow, a separate button
  beside it (`.toggle`, aria-label "More in {name}", `nav.more`), opens or closes the
  section**. Its link is active on that exact page only; on a page inside, the label is
  bright (`data-has-active`). `navLinks` counts these pages, so the parent opens on them.
  Sections without a page keep the whole row as the toggle.
- **The PvP menu** (`pvpNav.ts`, the user's order): Home · Character · Leaderboards (2v2,
  3v3, Solo Shuffle, Battleground Blitz, Rated Battlegrounds; each opens its whole ladder,
  and its arrow lists every class A–Z; a class opens its whole ladder (`…/<class>/all`)
  and its arrow its specs A–Z, like the PvE Specs; A–Z by English name from `gameOrder.ts`, shared with `pveNav`) · Stats (Spec Representation,
  Hero Talents, Cutoffs) · FOTM · Tier List · Archives. Links are `linkOptions(...)`, so

## 6. Styling

Colours are defined in three layers. Don't skip one.

1. **`src/styles/palette.ts`** is the only place hex values live. It holds the neutral
   dark scale (background `#0d1117`, text `#e6edf3`, highlight `#ffffff`), the
   `horde` (red) and `alliance` (blue) scales, the `gold` and `silver` trim scales, status
   colours, item quality colours and class colours.
   - **The faction colours come from the emblems** in `src/assets/icons/factions/`. In each
     scale, step `700` is the emblem colour itself (Horde `#930000`, Alliance `#002853`).
     The other steps keep that hue and change only lightness, because the emblem blue is
     too dark to see on the background. `500` is the accent: at least 3:1 on the
     background, and white text on it at least 5.8:1. Keep those ratios if you retune.
   - **Gold and silver come from the emblems' frames.** `factionTrim` maps Alliance to gold
     and Horde to silver.
2. **`src/styles/tokens.css`** holds the palette's values as shared CSS variables on `:root`:
   `--color-bg`, `--color-surface*`, `--color-text*`, `--color-border*`, `--color-accent*`,
   `--color-quality-<q>`, `--color-class-<kebab-class>`, `--color-rank-<rank>`, `--space-*`,
   `--radius-*`, `--icon-size-*` and `--font-*`. It is plain CSS, written from `palette.ts`;
   **`tokens.test.ts` fails if the two disagree**, so change a colour in both.
   - **`--color-accent*` follows the user's faction.** `<html data-faction="horde|alliance">`
     switches it, and the PreferencesProvider sets that attribute.
   - Use `--color-horde` and `--color-alliance` only for something that is always one
     faction (the toggle, a faction badge).
   - **`--color-trim*` also follows the faction:** gold for Alliance, silver for Horde.
     `--color-trim` is used for focus rings and `--color-trim-strong` for highlights.
     `--color-trim-muted` frames panels, the header, the toggle and game icons.
   - **`--color-border*` stays neutral.** Use it only for dividers inside content, such
     as table rows. Frames and outlines use trim.
   - `--color-accent-emblem` is the exact emblem colour, for large faction fills.
3. **Components** declare local variables that default to the shared tokens, and style
   with those. A component can then be re-coloured without changing the shared tokens:
   ```css
   .panel {
     --panel-bg: var(--color-surface);
     background: var(--panel-bg);
   }
   ```

**How styles are written** (the user's rule, 2026-11-26: no styling library, no inline styles):

- **Each component has its own `Component.module.css`** beside it (CSS Modules, built into
  Vite; class names are scoped). Import it as `styles` and use `className={styles.x}`; join
  classes with `cx()` (`src/lib/cx.ts`). Variants are classes (`styles.sm`) or data
  attributes styled in the module (`[data-state='ok']`, `[aria-expanded='true']`).
  `lineParts.module.css` is shared by `CharacterLine` and `GuildLine`, which must line up.
- **Global CSS** in `src/styles/`, imported once in `main.tsx`: `tokens.css`, `global.css`
  (reset, element defaults, `.sr-only`, `body.scroll-locked`), `gameColors.css`,
  `iconOptics.css`.
- **Colours from data** go through data attributes and `gameColors.css`, never `style`:
  `data-class-color={classColorKey(cls)}` (class colour), `data-rank={rank.id}` (PvP rank
  colour). Its rules start with `:root`
  so they outrank a module's own default colour (a module class and an attribute selector
  have the same specificity, and modules load later).
- **No `style={…}`.** The one exception is a value CSS can't know: `NavGlyph` sets
  `--glyph-url` to its icon's URL, which Vite hashes at build time. A static icon is named
  in CSS directly: `mask: url('../assets/icons/nav/search.svg') …` (Vite resolves it).
  `AppHeader` also publishes its measured height as `--header-height` on `<html>`.
- **Route folders hold no CSS** (the router scans them): a route's layout lives in a
  component (`AppLayout` for the frame).
- Tests: CSS is stubbed in Vitest except `src/styles/*.css` (`test.css.include`), which
  tests read with `?raw`.

When you add a colour, put it in the palette and in `tokens.css` (the test keeps them
together), then use the variable. Shared layout pieces are `Page`, `PageTitle`, `Panel` and
`Muted` in `src/components/Page.tsx`; widgets use `WidgetGrid` and `Widget`.

### Assets and asset styles

Assets live in `src/assets/` (`icons/`, `images/`, `fonts/`). The Rankwarden logo is
`images/logo/rankwarden-logo.svg` (header) and `rankwarden-emblem.svg`; favicons are in `public/`.
Navigation icons (`icons/nav/*.svg`) are monochrome `currentColor` SVGs coloured by the
faction accent, except `bosses.svg` (fixed fel green), which `NavGlyph` inlines. The guild
icons also carry colours but are drawn as masks on purpose (`inlineIcons.ts`). One-look PNG families read by path
with `iconUrl()`: `game-modes/` (pvp, pve, mplus, raid), `places/` (place-1..3 badges) and
`info/` (item-level, deaths, vantus-rune, gems, embellishments, enchants, tier-set, unknown, in the role icons' round frame) `pvp/brackets/` (named by bracket slug: 2v2, 3v3, rbg, shuffle, blitz; single-colour SVG
versions in `pvp/brackets/svg/`), `styles/`
(classic/modern header switch, per faction: `<style>-<faction>`) and `difficulty/`
(normal, heroic, mythic; SVG versions in `difficulty/svg/`, because `iconUrl` keys by path
without extension, so a same-named .png and .svg in one folder clash). See the assets
README. `src/assets/README.md` has the rules. The key concept:

- **Every icon family has a `modern` and a `classic` style:**
  `src/assets/icons/<family>/<style>/<name>.<ext>`. The user picks one with the preference
  `assetStyle` (default `modern`). The switch UI isn't built yet.
- **Never import icon files directly.** Use the family's mapper, so the style applies.
  `src/lib/assets.ts` loads every icon URL through one eager `import.meta.glob`, which
  gives URLs only; the files load lazily.
  - `styledAssetUrl(family, style, name)` returns the URL, falling back to the other
    style when that style lacks the file.
  - `styledAssetNames()` and `hasStyledAsset()` let tests check coverage.
- **Races:** `src/lib/wow/races.ts` maps every API shape to a race and gender:
  - race as an id, `"Night Elf"`, or `{ id, name }`;
  - gender as `"male"`, `"FEMALE"`, or `{ type }`.

  `raceIconUrl()` and `<RaceIcon race gender />` give the icon. The race id wins over the
  name, because names are localised.
  - The list covers 31 Blizzard ids in 26 races. Pandaren (24/25/26), Dracthyr (52/70),
    Earthen (84/85) and Haranir (86/91) have one id per faction.
  - Mythic+ data has **no gender**. `fallbackGender` (default `male`) picks the icon; pass
    `null` for no icon.
  - **Portraits are round and framed in faction colours:** Horde in silver trim around a
    red ring, Alliance in gold around blue (`palette.silver/gold/horde/alliance`). A race
    both factions play therefore has one file per faction, `<name>-<gender>-<faction>`
    (`panda-male-horde`). Pass the character's faction: `raceIconUrl(race, gender,
{ style, faction })` or `<RaceIcon race gender faction />`. Unknown or neutral picks
    Alliance. Single-faction races have no suffix and ignore `faction`.
    `raceIconFileName()` builds the name; the tests use it for coverage.
  - When a new race ships, add it to `RACES`, add its icons, and extend the id table in
    `races.test.ts`. Get the real ids from Rankwarden's `mplus_characters.profile.raceId`
    and `characters.profile.race`.

- **Race crests** are icons with a single look, at `icons/races/crests/<faction>/<name>-crest.png`.
  `raceCrestUrl(race, faction?)` and `<RaceCrest race faction />` give them; `iconUrl(path)`
  in `src/lib/assets.ts` reads icons that have no style.
  - A single-faction race (`Race.faction`) always uses its own folder.
  - A race both factions play uses the given faction, or either folder if none is given.
  - File names that differ from the slug are declared in `crestName`.
- **Honor badges:** `src/lib/wow/honor.ts` maps the PvP character's
  `honor: { level, honorableKills }` (or a bare level) to a badge. `HONOR_BADGES` is
  `{ tier, minLevel }`; a badge is shown from its level until the next one.
  - The thresholds came from the project owner, not from an API. Only tiers 1–21 have
    one. Tiers 22–33 are unmapped, so add a threshold before using them.
  - Below level 5, or with `honor: null`, there is no badge.
- **PvP ranks** (`src/lib/wow/pvpRank.ts`, `<PvpRankIcon rank />`). The bands came from the
  project owner.
  - **Past seasons:** `rankOfHistoryEntry(entry)` maps a `pvpHistory` entry's `tier`.
    Gladiator, Legend, Strategist and Battle Mender share the Gladiator icon; `rank-one` is
    any Rank 1 title. `bestRankInSeason(history, seasonId)` picks a season's best.
  - **Current rating:** `rankForRating({ rating, history, seasonId, rankOneCutoff })`:
    - below 1000 Unranked; Combatant from 1000; Challenger 1400; Rival 1800; Duelist 2100;
    - from 2300, Rank 1 at or above the ladder's Rank 1 cutoff;
    - else Gladiator if this character holds a Gladiator-type title for `seasonId`;
    - else Elite.
  - Achievements are account-wide. Titles with `earnedByThisCharacter: false` count only
    with `{ ownOnly: false }`.
- **Ids first.** Since Soulseeker 311b007, every answer that names a class, spec, race or
  hero talent tree also carries Blizzard's id: `classId`, `specId` (`activeSpecId` on
  the PvE character), `raceId`, `heroTalentId`. Pass the id to the mappers; names are
  the fallback for older shapes.
- **Specs:** `src/lib/wow/specs.ts` builds `SPECS` from spirit-link's `SPECIALIZATIONS`
  (ids, names, class ids, `role`, `subRole`). Never hand-maintain a spec table here. The
  slug is the name, letters only, as Soulseeker's ladders spell it. `resolveSpec(spec, cls?)` accepts:
  - an id (`specId`, Blizzard `activeSpec`);
  - a ladder name (`shuffle-mage-fire`);
  - a slug or name **with its class**, because holy, frost, restoration and protection
    each belong to two classes. Without the class it returns null.
- **Roles:** `src/lib/wow/roles.ts`, `<RoleIcon role subRole />` or `<RoleIcon spec cls />`.
  - Values are spirit-link's: `role` `tank | healer | dps`, `subRole` `melee | ranged`
    (dps only). `resolveRole` also reads Raider.io's `TANK | HEALING | DPS`
    (`activeSpecRole`). A sub-role implies dps; tanks and healers never have one.
  - `roleOfSpec(spec)` gives a spec's role and sub-role.
  - `specsMatching({ class, role, subRole })` lists the specs a role filter names, by the
    same rules as Soulseeker's `/pvp/leaderboard`, `/pvp/cutoffs` and
    `/pve/mplus-leaderboard` filters. Empty means Soulseeker answers 400 (a priest has
    no tank). Never send `role`/`subRole` together with `spec`.
  - Icons: `icons/roles/{tank,healer,dps,dps-melee,dps-ranged}.png`. `dps` is for a dps
    role whose sub-role is unknown.
- **Hero talents:** `src/lib/wow/heroTalents.ts` holds all 41 trees, with Blizzard ids
  taken from Rankwarden's `characters.profile.heroTalentTree`. It accepts a name (PvP
  boards' `heroTalents`), an id (`heroTalentId`), or `{ id, name }`; the id wins. Tree
  names are unique across classes. Mythic+ characters always have `heroTalents: null`.
- When Blizzard adds a spec, update spirit-link and add the spec's icon. When it adds a
  tree, add it to `HERO_TREES` with its id, plus its icon. The tests fail on a missing
  icon or a file that matches nothing.
- **Factions:** `src/lib/wow/factions.ts` maps `"horde"`/`"alliance"` (any case) and
  Blizzard's `{ type, name }`. Neutral and unknown values map to null.
  - `factionIconUrl()` and `<FactionIcon faction />` give the emblem.
  - `factionColorVars()` gives `var(--color-<faction>)` and `var(--color-<faction>-trim)`,
    a faction's **own** colours, independent of the user's choice.
  - **Never derive faction from race.** Blizzard's PvP profiles use the per-faction ids
    consistently, but Raider.io's Mythic+ `raceId` doesn't: Pandaren 24 appears on both
    sides, and so do Dracthyr 52, Earthen 84 and Haranir 86 (checked 2026-11-19). The
    faction is always sent directly.
- **Classes:** `src/lib/wow/classes.ts` maps every API shape to one of 13 classes:
  - the Soulseeker slug `"deathknight"` (PvP boards, stats, query params);
  - `classId` 1–13 and `className` `"Death Knight"` (Mythic+);
  - `{ id, name }` (Blizzard profile);
  - `null` for PvP characters Rankwarden hasn't enriched yet.

  `classIconUrl()` and `<ClassIcon cls />` give the icon. `classColorVar()` gives
  `var(--color-class-*)`, so class colours always come from the tokens.
  - The icon file name is the slug.
  - Every icon is now `.png`; the asset glob still accepts jpg/jpeg/svg/webp.

- **Icon sizes are shared across families.** Every game icon renders through
  `<GameIcon>` (`src/components/GameIcon.tsx`) at one of three sizes from
  `src/styles/iconSizes.ts` (also the CSS vars `--icon-size-*`):
  - `sm` 24px, inline with text (default);
  - `md` 40px, inside clickable filter pickers; the button adds padding to reach a 48px hit target;
  - `lg` 64px, page headers.
  - **Shape:** the default `square` box has a background and a 1px CSS border
    (`frame="horde|alliance"` recolours it in that faction's trim). Classes, specs, hero talents, races and roles are round art with their own
    frame (class-colour rim; faction trim on races; a bronze ring on roles), so their components pass `shape="round"`:
    a circle with no CSS border or background. Use `round` for any new self-framed round art.

  Source files should be 128x128 (2x of `lg`). Never give an icon a pixel size of its own.

- **Family tests** (`races.test.ts`) fail when an icon is missing without being listed in
  `KNOWN_MISSING`, when a listed gap has been filled, or when a file name matches no race.
  Copy this pattern for new families.

`public/` holds only files that need a fixed URL (`config.js`).

## 7. Configuration and preferences

- **Runtime config.** `index.html` loads `/config.js` before the app, which sets
  `window.__FARSEER_CONFIG__ = { soulseekerApiUrl }`. `src/config.ts` reads it first and
  falls back to `VITE_SOULSEEKER_API_URL`.
  - Locally, `public/config.js` is left empty, so `.env.local` applies
    (`VITE_SOULSEEKER_API_URL=http://localhost:3001`).
  - In the cluster, the Helm ConfigMap replaces `/config.js` from `runtimeConfig` in
    `values.yaml`. One image serves every environment. **Never bake environment URLs into the build.**
  - When you add a runtime setting, add it to `RuntimeConfig` in `src/config.ts`, to
    `public/config.js`, and to `runtimeConfig` in the chart values.
- **User preferences.** `src/preferences/` keeps them as one JSON object in localStorage
  under `farseer:preferences`, kept in sync across tabs.
  - When you add a preference, add it to `Preferences`, `defaultPreferences` and the
    validation in `readPreferences`. Read and write it with `usePreferences()`.
  - The inline script in `index.html` applies the faction before the page first draws, to
    avoid a colour flash. It reads the same key, so keep it in step if the structure changes.
- **Preferences now:** `faction` (horde | alliance), `assetStyle` (modern | classic),
  `gameMode` (pvp | pve, default pvp), `locale` (a language slug, or null until one is
  chosen, so a first visit follows the browser), and `lastPvpCharacter`,
  `lastPveCharacter`, `lastPveGuild` (`{ region, realm, name }` of the last such page
  opened, or null). `pvpBoardRegions` (`{ shuffle: 'eu' }`: the region last
  picked on each PvP bracket's leaderboard widget; unknown brackets or regions are dropped). The privacy policy lists what is
  stored: **update it in all eight languages when a preference is added.** `gameMode` and `locale` are read outside
  React by the redirects.
  `readPreferences` validates each field on its own and drops unknown keys.
- **localStorage keys:** `farseer:preferences` and `farseer:auth`. Prefix new keys with `farseer:`.

## 9. Traps on this machine (Windows)

- **An SVG that isn't well-formed XML shows nothing**, with no error: as a mask or an
  `<img>` it is just blank. The usual cause is `--` inside a comment (`<!-- uses
var(--color-trim) -->`), which XML forbids; the guild icons had it (fixed 2026-11-25).
  `src/lib/svgAssets.test.ts` parses every SVG under `src/assets/` and fails on one.

- **Drive-letter case.** Git Bash's working directory is `/d/...` (lowercase), while
  PowerShell and Node use `D:\`. Two consequences:
  - **Vitest** started from Git Bash loads itself twice and fails with "failed to find the
    current suite", or with every suite failing at its first `describe` ("Cannot read
    properties of undefined (reading 'config')", "no tests"). It can pass one run and fail
    the next, so a pass from Bash proves nothing. **Run Vitest from PowerShell**
    (`Set-Location D:\PersonalProject\Farseer`). Node 24 and 26 both pass there.
  - **Vite aliases** must point at the root-relative `/src`, never at an absolute path. An
    absolute path loaded the same module twice (once as `/src/...`, once as `/@fs/d:/...`).
    That created two React contexts and the error "usePreferences must be used within PreferencesProvider".
- **Avast re-signs HTTPS**, so `npm ci` inside Docker fails with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`.
  `npm run docker:build` passes the certificate as the BuildKit secret `extra_ca` from
  `DOCKER_EXTRA_CA` or `NODE_EXTRA_CA_CERTS`, and the latter is set on this machine.
  A plain `docker build` fails here. CI doesn't need the certificate.
- **PowerShell 5.1** `Set-Content -Encoding utf8` writes a BOM. Strip it afterwards with
  `sed -i '1s/^\xEF\xBB\xBF//' file`, or edit with the file tools instead.
  `Get-Content -Raw` reads a UTF-8 file without a BOM as ANSI, so a read-modify-write
  turns `→` into `â†’`. Don't rewrite source files through PowerShell.
- **The Vite dev server misses quick edits.** A second edit to a file shortly after the
  first is sometimes not picked up, so the browser runs stale code (seen 2026-11-24: `/`
  redirected to `/undefined`). Before trusting what the browser shows, compare
  `curl localhost:5173/src/<file>` with the file, and `touch` any file that's behind.
  The user usually has a dev server on 5173 already, and Soulseeker's CORS allows only
  that port, so test against theirs; a second server goes to 5174 and its API calls fail.
- **SVG in CSS `url()`.** Name a static icon in the module's CSS by its relative path
  (`url('../assets/icons/nav/search.svg')`); Vite resolves and inlines it. Only an icon chosen
  at runtime goes through a custom property (`--glyph-url`, built in TypeScript with double
  quotes: Vite's inlined `data:` URLs contain single quotes).
- **GitHub Packages.** `.npmrc` maps `@denipetrov` to `npm.pkg.github.com`; the token
  lives only in `~/.npmrc` (`//npm.pkg.github.com/:_authToken=…`). Never commit a token.
- **Long heredocs** in the Bash tool can fail to parse, and when they do, nothing is
  written. Use the Write tool for multi-file scaffolding.
- **Helm isn't installed.** Lint and render the chart through Docker:
  `MSYS_NO_PATHCONV=1 docker run --rm -v "D:/PersonalProject/Farseer/deploy/helm:/charts" alpine/helm:latest lint /charts/farseer --set image.tag=ci`
- **`… | tail` hides exit codes.** A failed `docker build` piped to `tail` reports success.
  Check the output, or redirect it to a file and test `$?`.

## 10. Build, CI/CD and deployment

**The image** (`Dockerfile`) builds with Node 24, then serves the files with
`nginxinc/nginx-unprivileged` (uid 101, port 8080). `deploy/nginx/default.conf` defines how they are served:

- unknown paths fall back to `index.html`, so the router can handle them;
- `/assets/*` is immutable for a year;
- `/` and `/config.js` are `no-cache`;
- `/healthz` serves liveness and readiness;
- gzip and security headers are on.

It runs with a read-only root filesystem, `/tmp` as an emptyDir, and all capabilities
dropped. That setup was smoke-tested locally on 2026-11-17.

**Workflows:**

| Workflow      | Trigger                                        | What it does                                                                                                                           |
| ------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`      | pull request, push to `main` or `develop`      | Typecheck, lint (no warnings allowed), format, tests, build. Helm lint and render, `bash -n` on the scripts, image build without push. |
| `release.yml` | tag `v*`                                       | Pushes `ghcr.io/denipetrov/farseer:<tag>` and `:sha-<commit>`. Never `latest`.                                                         |
| `deploy.yml`  | manual (`image_tag`), environment `production` | doctl, then `create-secrets.sh`, then `deploy.sh`                                                                                      |

**Chart** (`deploy/helm/farseer`): one release, `farseer`, in namespace `farseer`, on the
same DigitalOcean cluster as Rankwarden and Soulseeker. It contains:

- a Deployment;
- an HPA with 2–4 replicas;
- a PDB;
- a Service (port 80 → 8080);
- an HTTPRoute for `rankwarden.gg` on Gateway `public` in namespace `gateway`;
- a NetworkPolicy: ingress only from the gateway, no egress;
- a ConfigMap that serves `config.js`. Its checksum is a pod annotation, so a config change rolls the pods.

`image.tag` is required; rendering without it fails on purpose.

**Private packages.** `npm ci` needs a GitHub Packages token for `@denipetrov/spirit-link`:

- CI sets `NODE_AUTH_TOKEN` (`PACKAGES_TOKEN`, else `GITHUB_TOKEN`) with
  `setup-node`'s `registry-url`.
- The image build takes it as the BuildKit secret `npm_token`. CI and release pass it;
  `npm run docker:build` reads `NPM_TOKEN` or `~/.npmrc`. It ends up in no layer.
- `GITHUB_TOKEN` can read the package only after Farseer is granted access under the
  package's "Manage Actions access" setting. Otherwise add a `PACKAGES_TOKEN` secret
  with `read:packages`. This mirrors Soulseeker.

**Before the first deploy**, these are the user's actions, not an agent's:

- the GitHub `production` environment, with secrets `DIGITALOCEAN_ACCESS_TOKEN`,
  `GHCR_USERNAME` and `GHCR_TOKEN`, and the variable `DO_CLUSTER_NAME`;
- a Gateway listener for `rankwarden.gg`;
- Soulseeker's `CORS_ORIGINS` listing every Farseer hostname.

**Not verified yet:** the GitHub workflows have never run, and no deploy to a real or kind
cluster has been done.
